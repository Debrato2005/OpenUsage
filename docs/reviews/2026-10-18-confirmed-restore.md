# Confirmed restore and executor recovery

Confirmed restore now runs through the actual Tauri application on Linux. The user reviews current and incoming counts, then checks an explicit approval box. The native command also requires literal confirmation. An opaque preview token can authorize only one attempt. AT-32 remains partial until checkpoint recovery and the remaining acceptance checks pass.

The SQLCipher transaction checks the saved revision after acquiring its write lock. It validates the supported source records, copies trusted columns, and checks schema, relations, domains, and counts before commit. It preserves account observation times. Restored profiles require authentication, and monitoring stays stopped. The source SQLite connection closes and its image buffer clears before the live transaction commits.

Archive imports receive new private UUID homes for every profile, including archived profiles. Existing homes remain intact. Rust synchronizes new directories and checks available bytes and inodes on the actual destination filesystems. Failure cleanup removes only an empty directory whose retained descriptor still matches the path. Missing, changed, or corrupt recovery checkpoints stop Apply before it changes records.

Checkpoint verification keeps SQLCipher 4 and the original protected key. Ordinary read-only ATTACH can create WAL sidecars. Closed private checkpoints therefore use an internally encoded immutable URI, with no-follow descriptors and identity checks. The live database always keeps normal WAL semantics. The reader authenticates encrypted pages and checks supported records without a full image allocation. Only the separate recovery image reader has the existing 5 GiB memory limit. See the [SQLite URI documentation](https://www.sqlite.org/uri.html) and [SQLCipher ATTACH documentation](https://www.zetetic.net/sqlcipher/sqlcipher-api/#attach).
